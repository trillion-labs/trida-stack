# Resolved dependency set for the GravityOCR SGLang server env (inference/gravityocr/serve.sh).
#
# requirements.in declares what the server env depends on; this records what that resolves to.
# setup.sh installs exactly these pins, with --no-deps --no-build and nothing re-resolved, in two
# steps, then installs SGLang itself, editable, from upstream sgl-project/sglang at BASE_COMMIT.txt
# with gravityocr_selfspec.patch applied:
#   1. every pin except sglang and the four +cu128 builds, from https://pypi.org/simple only;
#   2. the four +cu128 builds, from https://download.pytorch.org/whl/cu128 only;
#   3. SGLang, built --offline --no-build-isolation with the build backend pinned here (setuptools,
#      setuptools-scm, vcs-versioning, wheel, packaging), so the build fetches nothing.
# setup.sh enforces the two sources: it passes the index explicitly and ignores uv config files and
# uv's index environment variables. The pins carry no hashes, so a source is trusted by its URL.
# A single install across both indexes would pick torch 2.9.1+cu128 for "torch==2.9.1". This lock,
# like the GPU-validated env it starts from (below), uses the PyPI torch 2.9.1 build. The lock itself
# raises 11 pins above that env and takes the four PyTorch-index builds as +cu128 builds of the same
# versions (that env has +cu129 ones; see the end of this header). A fresh setup.sh run with this lock
# on H100 (2026-11-12) gave the same greedy outputs as that env on 100 OCR crops, in self-spec and
# causal mode, and torchaudio, torchvision and torchao import.
#
# Why sglang==0.5.10 is listed although PyPI's sglang is never installed: the resolver needs SGLang's
# dependency metadata (it is what pins torch 2.9.1, transformers 5.3.0 and flashinfer-python
# 0.6.7.post2), and scanners reading this file should see the real base version, 0.5.10, and report
# its advisories. The advisories still open against these pins, and why each is acceptable here,
# are recorded in docs/supply-chain/exceptions.md.
#
# Named *-lock.txt rather than .lock so syft's requirements cataloger matches it.
#
# Generated with uv 0.11.27, run in this directory:
#   uv pip compile requirements.in \
#     --override overrides.txt \
#     -c validated-freeze.txt \
#     --exclude-newer 2026-10-30T12:00:00Z \
#     --python-version 3.12 \
#     --python-platform x86_64-manylinux_2_28 \
#     --extra-index-url https://download.pytorch.org/whl/cu128 \
#     --index-strategy unsafe-best-match \
#     --no-build \
#     --no-emit-index-url \
#     --no-header \
#     -o requirements-lock.txt
#
# validated-freeze.txt, committed next to this file, is the pip freeze of the GPU-validated server
# env (env/sglang_venv_freeze.txt in github.com/trillion-labs/GravityOCR at 4ab5d54) minus every
# package that requirements.in floors with ">=", with torchao, torchaudio, torchcodec and torchvision
# as +cu128 builds of the frozen versions; the "-c validated-freeze.txt" annotations below come
# from it. --exclude-newer fixes the resolution date, so the floored packages and the build backend,
# which the freeze does not pin, resolve to the releases of that date: the command above reproduces
# everything below this header byte for byte. Move the cutoff only on purpose, and review the pins
# that change.
#
# Python 3.12 (not trida's 3.10): filelock 4.2.4, pillow 13 and multidict 7.2 need >= 3.11.
# Resolution needs the cu128 index (with unsafe-best-match) only for torchao, torchaudio, torchcodec
# and torchvision. torch itself is the PyPI 2.9.1 build (CUDA 12.8 runtime), and the four builds must
# match it: torchaudio refuses to import when its CUDA differs from torch's. With the +cu129 builds of
# the validated env, `import torchaudio` failed and SGLang dropped the models that import it
# (MiDashengLM) at startup; OCR never uses torchaudio.
