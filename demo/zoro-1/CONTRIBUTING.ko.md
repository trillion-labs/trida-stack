# Zoro-1 데모 기여 가이드

[English](CONTRIBUTING.md) · 한국어

Zoro-1로 뭔가 만들어 주셔서 고맙습니다. 이 문서는 데모를 제안하는 방법, 데모 폴더에 꼭 들어가야 하는 것,
머지 전에 리뷰어가 확인하는 내용을 다룹니다. 짧은 요약은 [README](README.md#add-a-demo)에 있고, 여기는 전체
버전입니다.

## 1. 시작하기 전에

- **이미 있는 데모부터 확인해 주세요.** [README](README.md)의 표에 데모 목록이 있습니다. 새 데모는 기존 데모가
  하지 않는 일을 하거나, 같은 일이라도 다른 사람들을 위한 것이면 좋습니다.
- **규모가 크거나 애매하면 먼저 물어봐 주세요.** [Discussions](https://github.com/trillion-labs/trida-stack/discussions/categories/ideas)나
  이슈에 한 문단이면 충분합니다. 무엇을 하는지, 누구를 위한 건지, Zoro-1의 어떤 기능을 쓰는지 적어 주세요.
  작은 데모는 바로 풀 리퀘스트를 올려도 됩니다.
- **저장소 전체의 [CONTRIBUTING.md](../../CONTRIBUTING.md)도 읽어 주세요.** 라이선스, 비상업 커널 관련 주의사항,
  풀 리퀘스트 절차 같은 공통 규칙이 있습니다. 데모도 저장소의 나머지와 마찬가지로 Apache-2.0입니다.

좋은 Zoro-1 데모는 이렇습니다.

- 가능하면 **decision head를 씁니다.** 보정된 확률은 그대로 게임 장치가 됩니다. 점수, 게이지, 순위, 심판,
  확률 굴리기 같은 것들이요. 채팅만으로는 어떤 모델이든 할 수 있지만, decision은 Zoro-1만의 강점입니다.
- 처음 보는 사람도 **1분 안에 재미있거나 쓸모 있다고** 느낍니다.
- **노트북에서 돌아갑니다.** Mac에서 Zoro-1은 요청을 한 번에 하나씩 처리하니, 수백 명이 아니라 몇 명이 쓰는
  상황을 기준으로 설계해 주세요.
- **Zoro-1이 잘하는 것에 맞춥니다.** 4B 모델이라 긴 자유 서술보다 짧고 구조화된 출력이 훨씬 잘 됩니다. 약한
  부분이 있으면 피해 가세요. 저희가 해 보니 한국어 캐릭터 채팅과 삼행시는 약했습니다. 예를 들어 choice
  선택지에 짧은 영어 설명을 붙이는 식으로 보완할 수 있습니다.

## 2. 폴더 구조

[`_template/`](_template/)을 `demo/zoro-1/<데모-이름>`으로 복사하세요.

```
demo/zoro-1/<데모-이름>/
  README.md            필수, 4장 참고
  pyproject.toml       필수: 이름, Apache-2.0, 의존성, 실행 스크립트, "test" extra
  <패키지>/             코드
  tests/               필수: mock 모드에서 통과
  docs/                선택: README용 스크린샷이나 GIF
  uv.lock              권장: 커밋해 두면 `uv run`이 어디서나 똑같이 동작합니다
```

- **이름:** 폴더는 소문자와 대시(`zoro-tarot`), 파이썬 패키지는 밑줄(`zoro_tarot`)을 씁니다. `pyproject.toml`의
  패키지와 스크립트 이름도 바꾸고, `my_demo`라는 이름은 남기지 마세요.
- **자급자족:** 데모에 필요한 건 전부 데모 폴더 안에 둡니다. 실행 중에 다른 데모나 저장소의 다른 부분을
  import하지 마세요. (테스트에서 Zoro-1 요청 파서를 읽는 건 괜찮습니다. 5장 참고.) 다른 데모의 코드가
  필요하면 복사해 오세요.
- **Python 3.10 이상, [uv](https://docs.astral.sh/uv/)로 실행:** 깨끗한 컴퓨터에서도 폴더 안에서
  `uv run <스크립트>`만으로 실행되어야 합니다. 의존성은 적게, 잘 알려진 것으로만 쓰세요.
- **웹 UI는 꼭 필요하지 않으면 빌드 단계 없이 만드세요.** zoro-draw처럼 파이썬 앱이 서빙하는 평범한 HTML, CSS,
  JavaScript가 다른 사람이 읽고 고치기 가장 쉽습니다.

## 3. Zoro-1과 통신하기

- **HTTP로만 통신합니다.** 사용자가 따로 띄운 Zoro-1 서버에 decision은 `POST /v1/systemone`, 채팅은
  `POST /v1/chat/completions`로 요청합니다. 데모 안에서 모델 가중치를 직접 불러오지 마세요. 그래야 같은
  데모가 MLX 서버(Mac)와 SGLang 서버(GPU) 양쪽에서 수정 없이 돌아갑니다.
- **서버 주소는 `--model-url` 옵션이나 `ZORO_URL` 환경 변수로 받습니다.** `model` 필드의 기본값은 `zoro-1`로
  두세요.
- **mock 모드는 필수입니다.** Zoro-1을 흉내 내는 `--mock` 옵션을 만들어 주세요. 테스트가 흔들리지 않도록 결과는
  결정적이어야 합니다. 모델이나 GPU 없이도 누구나 데모를 써 볼 수 있어야 하고, CI도 테스트할 수 있어야
  합니다. `_template/my_demo/zoro.py`에 mock이 들어 있는 작은 클라이언트가 있으니 복사해 쓰셔도 됩니다.
- **실패는 눈에 보이게 하세요.** 모델 서버가 꺼져 있거나 요청이 실패하면 UI나 콘솔에 알려 주세요.
  zoro-draw는 시작할 때 경고를 출력하고, 판정에 실패한 라운드에는 오류를 보여 줍니다. 진짜 답처럼 보이는
  기본값으로 조용히 넘어가면 안 됩니다.
- **모델 서버는 외부에 노출하지 마세요.** 웹 앱이라면 브라우저는 데모 앱과 통신하고, 데모 앱이 Zoro-1과
  통신해야 합니다. Zoro-1 포트를 공개하지 말고, 비밀값이나 숨겨야 할 정답을 브라우저로 보내지 마세요.
- **동시 요청:** MLX 서버는 요청을 하나씩 처리합니다. `--concurrency` 제한을 두세요(Mac에서는 1이 안전하고,
  SGLang은 요청을 묶어 처리하니 더 높여도 됩니다). 기다리는 동안 화면이 멈춘 것처럼 보이지 않게 "Zoro가
  생각하는 중…" 같은 상태를 보여 주세요.
- **decision 요청 팁:**
  - `state`에서 잘 바뀌지 않는 부분을 앞에 두세요. 서버가 state 앞부분을 캐시하기 때문에 반복 호출이 빨라집니다.
  - 같은 state에 대한 질문이 여러 개면 한 요청에 묶으세요. prefill을 한 번만 합니다.
  - 상호작용이 있는 곳에서는 `"reasoning": false`를 쓰세요.
  - 이미지는 요청당 한 장, data URL로 보냅니다. 기본 최대 크기는 448×448입니다. 그림은 흰 배경으로 보내세요.
  - 선택지 설명(`"criteria": {"key": "설명"}`)이 정확도를 높이는 가장 좋은 수단입니다.
- **채팅 요청 팁:** 빠른 답이 필요하면 `"chat_template_kwargs": {"enable_thinking": false}`를 보내고,
  `max_tokens`에 상한을 두고, 답이 중간에 잘리거나 비어 있는 경우도 처리하세요.

## 4. README

모든 데모 README에는 아래 섹션이 이 순서로 들어갑니다. 템플릿에서 복사해 쓰세요.

1. **제목과 한두 문장 소개:** 무엇이고 왜 재미있거나 쓸모 있는지.
2. **스크린샷이나 GIF:** 가능하면 실제 모델로 찍어 주세요. mock 모드로 찍었다면 이미지 아래에 그렇다고 적어 주세요.
3. **Zoro-1을 어떻게 쓰는지:** 사용하는 엔드포인트와 질문 타입, 그리고 실제 요청 본문 하나.
4. **실행 방법:** 실제 Zoro-1 서버로 실행하는 명령과 `--mock`으로 실행하는 명령. 모델 띄우는 방법은 반복하지
   말고 [Run Zoro-1](README.md#run-zoro-1)로 링크하세요.
5. **파일 구성:** 무엇이 어디 있는지 짧은 표로.
6. **테스트:** 테스트 실행 명령.

README는 영어로 써 주세요. 한국어 섹션이나 별도의 `README.ko.md`도 환영합니다. 이미지는 작게(최대 수백 KB)
유지해 주세요.

## 5. 테스트

- 데모 폴더에서 `uv run --extra test pytest -q`가 **mock 모드로**, 모델이나 네트워크 없이 통과해야 합니다.
- 실행되는지만 보지 말고 데모의 로직(점수 계산, 규칙, 모델 출력 파싱)을 테스트하세요.
- **요청을 Zoro-1의 파서로 검증하세요.** [`inference/zoro-1/decide_request.py`](../../inference/zoro-1/decide_request.py)를
  `pytest.importorskip`으로 불러와 실제로 보내는 요청 본문을 검사하는 테스트를 넣어 주세요
  (`_template/tests/test_demo.py` 참고). 실행은 이렇게 합니다.
  ```sh
  PYTHONPATH=../../../inference/zoro-1 uv run --extra test pytest -q
  ```
  실제 서버에서 누가 돌려 보기 전에 요청 형식 실수를 잡아 줍니다.
- 풀 리퀘스트를 올리기 전에 **실제 Zoro-1 서버로 한 번 실행해 보고**, PR에 그렇다고 적어 주세요.

## 6. 콘텐츠와 안전

데모는 공개되고, 여럿이 함께, 회사나 무대에서 플레이하는 경우가 많습니다.

- 플레이어가 보는 모든 것(프롬프트, 덱, 캐릭터, 시나리오, 예시 출력)은 누구에게나 보여 줄 수 있어야 합니다.
  성적인 내용, 괴롭힘, 혐오, 실존하는 일반인을 겨냥한 내용은 안 됩니다. 아슬아슬한 유머는 괜찮지만 잔인한
  건 안 됩니다.
- **실존 인물과 브랜드:** 실존 인물이나 단체를 사칭하지 말고, 실제 서비스로 오해할 만한 페이지(로그인, 결제,
  공식 안내문)를 만들지 마세요.
- **채팅 캐릭터**에는 PG-13을 지키고 성적인 요청은 넘기라고 지시해야 합니다. 게임 설정 밖에서 진지하게
  물으면 사람이라고 주장하지 않아야 합니다.
- **플레이어 데이터:** 데모에 필요한 것 이상은 모으지 마세요. 게임 기록을 남긴다면(프롬프트 개선이나 학습
  데이터용 등) 기본값은 꺼 두고, 무엇을 기록하는지 README에 적고, 기록 파일은 절대 커밋하지 마세요.
- 폴더에 **비밀값(토큰, API 키), 모델 가중치, 큰 데이터셋**을 넣지 마세요.
- 저작권: 저작권이 있는 이미지, 가사, 긴 글은 넣지 마세요. 이름이나 짧은 언급(밈 이름, 속담)은 괜찮습니다.

## 7. 풀 리퀘스트 체크리스트

PR 설명에 복사해 넣으세요.

```markdown
- [ ] 폴더는 `demo/zoro-1/<이름>`, 패키지와 스크립트 이름을 템플릿에서 바꿈
- [ ] 자급자족; 폴더에서 `uv run`으로 실행됨
- [ ] `--mock`이 모델 없이 동작; 실제 서버는 `--model-url` / `ZORO_URL`
- [ ] mock 모드에서 테스트 통과; 요청이 Zoro-1 파서를 통과 (`PYTHONPATH=../../../inference/zoro-1`)
- [ ] 실제 Zoro-1 서버(MLX 또는 SGLang)로 실행해 봄: ___
- [ ] README에 소개, 스크린샷/GIF, Zoro-1 사용 방식, 실행, 파일, 테스트가 있음
- [ ] `demo/zoro-1/README.md` 표에 한 줄 추가
- [ ] 누구에게나 보여 줄 수 있는 콘텐츠; 비밀값, 가중치, 기록, 개인정보 없음
- [ ] Apache-2.0
```

## 8. 리뷰와 머지 이후

- 메인테이너가 [COMMUNITY.md](../../COMMUNITY.md)의 응답 기준 안에서 리뷰합니다. 리뷰에서는 위 체크리스트를
  확인하고, 테스트를 돌리고, 보통 데모를 한 번 플레이해 봅니다.
- 다른 사람의 데모에 대한 작은 수정(버그 수정, 새 덱이나 프롬프트)은 언제든 PR로 올려 주세요. 큰 변경은
  먼저 이슈로 데모 작성자에게 물어봐 주세요.
- Zoro-1 API가 바뀌면 메인테이너가 데모들의 요청을 고칩니다. 오랫동안 고쳐지지 않은 데모는 누군가 고칠
  때까지 표에서 빠질 수 있습니다.
- 질문은 [Discussions · Q&A](https://github.com/trillion-labs/trida-stack/discussions/categories/q-a)에 올려 주세요.
