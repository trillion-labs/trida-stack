# Channel matrix

어떤 문의가 **어느 시스템에서 완결되는지**를 선언합니다. 채널을 늘리는 것이 접근성을
높이지 않습니다 — 같은 질문이 여러 곳에 복제되고 답변이 갈리면 검색 결과마다 다른
결론이 남습니다.

**한 문의의 기준 항목은 하나.** 다른 채널에는 원문을 복제하지 말고 URL과 짧은 맥락만.

| 문의 유형 | 기준 채널 | 보조 채널 | 전환 조건 | 목표 응답 |
|---|---|---|---|---|
| 코드 결함 (설치·API·CI) | GitHub Issues | 채팅 | 재현 절차 확인 후 Issue | 영업일 2일 |
| 기능 아이디어 | GitHub Discussions · Ideas | 채팅 | 구현 범위 합의 시 Issue | 주 1회 분류 |
| 사용법 Q&A | GitHub Discussions · Q&A | 채팅 | 3회 반복되면 FAQ/문서 | 영업일 2일 |
| 모델 동작·가중치·평가 | 해당 HF 저장소 Community | GitHub | 특정 model revision과 연관 | 영업일 3일 |
| 여러 모델을 아우르는 ML 질문 | HF Forum | 채팅 | — | 보장 없음 |
| 기여 작업 협의 | Issue ↔ PR | 채팅 | — | 영업일 2일 |
| 장기 설계 결정 | GitHub Discussions (공개 기록) | 회의·채팅 | 결정 요약과 근거를 기록 | 공고된 기간 |
| 보안 취약점·개인정보 | SECURITY.md 비공개 경로 | **없음** | 공개 금지 | 즉시 분류 |

## 어디로 보낼지 판단하는 순서

1. 특정 **코드 변경**으로 추적해야 하는가? → GitHub Issue/PR
2. 특정 **모델 revision**에 묶이는가? → 해당 HF 저장소 Community
3. 아직 **작업 범위가 없는** 공개 아이디어인가? → GitHub Discussions
4. **빠른 확인과 관계 형성**이 핵심인가? → 채팅
5. **취약점·신상·개인정보**인가? → 공개 채널이 아닌 검증된 비공개 경로

판단 예시: 모델이 잘못된 출력을 낸다는 보고가 오면, 먼저 **라이브러리 버전과 모델
revision을 고정**합니다. 여러 모델에서 같은 API 오류가 재현되면 GitHub Issue로,
한 모델 카드·가중치에만 해당하면 HF Discussion으로 갑니다. 데이터 샘플에 개인정보가
있으면 **공개 토론을 중단하고** 비공개 삭제 절차로 전환합니다.

## 전환할 때 남기는 것

사용자를 "잘못된 곳에 썼다"고 나무라지 않습니다. 새 기준 항목을 만들 수 있게 돕고,
전환 댓글에 **분류 이유 / 새 URL / 다음 담당자 / 원 채널의 상태**를 씁니다.

> 이 현상은 특정 모델 하나가 아니라 라이브러리의 로딩 경로에서 재현되어 GitHub
> Issue [URL]에서 추적하겠습니다. 이 Discussion은 중복 답변을 막기 위해 닫고,
> 해결 버전이 나오면 결과를 다시 연결하겠습니다.

전환 작업은 [`community_to_issue`](../../.github/ISSUE_TEMPLATE/community_to_issue.yml)
양식으로 합니다 — 기억해서 하는 일이 아니라 양식 작업으로 만들어 둡니다.

## 알림 설계

모든 commit·PR·댓글을 채팅에 보내면 사람이 읽지 않습니다. **행동 가능한 것만** 보냅니다.

- 새 릴리스와 중요한 호환성 변경
- 새 보안 공지, 지원 버전 변경
- **48시간 이상 담당자가 없는 질문** (자동 — `stale-unanswered.yml`)
- `help wanted` 또는 `good first issue` (자동 — `notify-labeled.yml`)
- 모델·데이터 카드의 중대한 변경

**양방향 자동 복제 봇은 쓰지 않습니다.** 삭제·편집·차단 상태와 개인정보가 어긋납니다.
기본은 알림과 링크이고, 원문은 기준 시스템에만 둡니다.
